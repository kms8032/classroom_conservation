이 파일은 `classroom_conservation` 저장소의 `v2/` 폴더(강의실 VLM v2)에서 작업할 때 참고하는 프로젝트 정의서입니다.

## 프로젝트 개요

강의실 카메라 영상으로 **좌석 점유**와 **강의실 인원 수**를 실시간으로 판단해, 관리자에게 현황을 보여주는 시스템입니다.

- **v1** (2026 산학연협력 EXPO 전시 버전): https://github.com/HyoChan1117/person-count
  - YOLO-pose + Claude API, 10분 단위 순간 캡처, 앉음/서 있음 판단 기반 좌석 점유
  - 데이터는 JSON 파일로만 관리 (점유 기록은 매주 월요일 초기화, 원자적 쓰기·잠금 없음)
- **v2** (`classroom_conservation/v2/`): https://github.com/kms8032/classroom_conservation
  - v1을 고쳐 쓰지 않고 **새로 작성**한다. ...
  - `collect/auto_dataset_collect.py`는 학습용 사진 수집 스크립트로, v2 코드와 분리해서 유지한다.

### 코드 작성 규칙

- **1학년이 읽고 따라갈 수 있는 코드**를 우선한다. 짧고 영리한 코드보다 명확한 코드.
- 주석과 docstring은 **한국어**로, "무엇을"보다 **"왜"** 를 적는다.
- 파일 하나에 역할 하나. 파일·클래스 이름만 보고 역할을 알 수 있게 한다.
- 좌석처럼 상태를 갖는 대상은 클래스로 표현한다 (예: `Seat` 클래스에 상태와 타이머).
- 카메라 계정·비밀번호·IP는 **반드시 저장소 루트의 `.env`** 로 관리하고 커밋하지 않는다. v2 코드는 루트 `.env`를 읽는다 (`v2/`에 따로 만들지 않음). ...
- RTSP는 TCP로 고정한다: `import cv2` 전에 `os.environ["OPENCV_FFMPEG_CAPTURE_OPTIONS"] = "rtsp_transport;tcp"`
- 비밀번호의 특수문자는 `urllib.parse.quote(pw, safe="")`로 인코딩한다.

### 데이터 저장 규칙 (JSON + SQLite)

데이터는 **세 곳**에 나눠 둔다. 기준: 사람이 열어서 고치는 것은 JSON, 프로그램이 계속 쌓는 것은 SQLite, 지금 이 순간의 상태는 메모리.

| 저장 위치                           | 무엇을                                                   | 왜                                                                                          |
| ----------------------------------- | -------------------------------------------------------- | ------------------------------------------------------------------------------------------- |
| **JSON** (`v2/config/`)             | 좌석 정의·ROI, 배치도, 교탁·복도 ROI 같은 **고정 설정**  | 사람이 직접 열어 보고 고치기 쉽고, Git으로 변경 이력을 볼 수 있음                           |
| **메모리** (`Seat` 객체 등)         | **실시간 좌석 상태**, 현재 인원                          | 0.5초마다 바뀌는 값을 파일에 매번 쓰면 느리고 충돌이 남. API가 메모리 값을 바로 응답        |
| **SQLite** (`v2/data/classroom.db`) | 1분 단위 요약 로그, VLM 강의실 상태 같은 **쌓이는 기록** | 기록이 늘어도 파일 전체를 다시 쓰지 않고, 기간·요일·시간대별 통계를 SQL로 바로 뽑을 수 있음 |

- 실시간 상태는 **파일(JSON·SQLite)에 덮어쓰지 않는다.** 서버가 재시작되면 좌석은 모두 "비어 있음"에서 다시 시작한다 (1분 안에 실제 상태로 채워지므로 허용).
- SQLite 기록은 **지우지 않고 계속 보관**한다 (v1처럼 매주 초기화하지 않음).
- SQLite에 쓰는 코드는 **저장 담당 클래스 한 곳**에만 둔다. 다른 파일에서 직접 `sqlite3`로 쓰지 않는다.
- 연결 시 **WAL 모드**를 켠다 (`PRAGMA journal_mode=WAL;`) — 기록하는 중에도 웹이 통계를 읽을 수 있게 하기 위함.
- 표 구조(CREATE TABLE)는 `v2/` 안의 한 파일에 모아 두고, 프로그램 시작 시 `CREATE TABLE IF NOT EXISTS`로 만든다.
- DB 파일은 커밋하지 않는다 (루트 `.gitignore`의 `data/` 규칙으로 이미 제외됨). 반대로 `v2/config/`의 JSON은 커밋한다.
- SQL은 문자열을 이어 붙이지 말고 `?` 자리표시자를 쓴다 (`cur.execute("... WHERE room = ?", (room,))`).

## 핵심 설계 (확정)

### 1. 판단 방식: 순간 캡처 → 실시간

RTSP를 **상시 연결**하고 카메라별 스레드로 **최신 프레임만 유지**한다. YOLO를 짧은 간격으로 반복 실행한다.

### 2. 좌석 점유 (일반 카메라)

- YOLO-pose로 사람을 탐지하고, **bbox 중심점이 좌석 ROI(다각형) 안에 있으면 "감지"**
- **자세(앉음/서 있음)는 판단하지 않는다.** 의자·책상·사람에 가려서 판단이 어렵기 때문
- 두 카메라에 겹쳐 보이는 좌석은 **어느 한쪽이라도 감지하면 감지**
- 좌석 상태는 시간 조건으로 바뀐다:

```
[비어 있음] ──(ROI 안에 5초 이상 연속 감지)──▶ [점유]
     ▲                                          │
     │                                     (감지 끊김)
     │                                          ▼
     └──────(1분 동안 계속 감지 안 됨)──── [확인 중]
                                                │
               [점유] ◀──(1분 안에 다시 감지)───┘
```

- 진입 대기 5초 동안은 화면에 **비어 있음** 그대로 표시 (지나가는 사람을 거르기 위함)
- 떠난 뒤 1분 동안은 **확인 중**으로 표시 (가려져서 잠깐 안 보이는 경우를 거르기 위함)
- 확인 중에 다시 감지되면 5초를 기다리지 않고 바로 점유로 복귀
- 진입 대기 5초 중 감지가 **1초 이하로 끊긴 것은 계속 감지된 것으로 본다** (`ENTER_GAP_SEC`). YOLO가 한두 프레임 놓칠 때마다 5초를 처음부터 다시 세지 않기 위함. 값은 실시간 데이터를 보고 조정

**기준점은 bbox 중심 (확정, 2026-11-03)**

- 카메라 위치상 엉덩이 등 키포인트가 실제로 보이지 않는 경우가 많고, pose 모델은 가려진 키포인트도 위치를 추측해서 내놓기 때문에 기준점으로 믿기 어렵다
- 좌석 ROI도 v1에서 bbox 중심 기준으로 쓰던 것이라 기준점과 맞는다
- 모델은 pose를 유지하되, 엉덩이 키포인트 유무는 **판정에 쓰지 않고 기록만** 한다. 실험 v3에서 오판의 엉덩이 검출률(43%)이 실제 사람(89%)보다 낮아, 나중에 "재확인 조건"으로 쓸 수 있는지 실시간 데이터로 확인하기 위함

**카메라가 끊겼을 때**

- 좌석을 볼 수 있는 카메라가 하나도 없으면 그 좌석은 **"카메라 연결 실패 · 재접속 중"** 으로 표시한다. 마지막 상태를 계속 보여주면 틀린 정보일 수 있고, 비어 있음으로 바꾸면 고장이 빈 좌석처럼 보이기 때문
- 이 표시는 좌석 상태(비어 있음/점유/확인 중)와 **따로** 관리한다. 점유 판단과 카메라 고장은 다른 문제라서 상태 그림에 섞지 않는다
- 두 카메라에 겹쳐 보이는 좌석은 한 대라도 살아 있으면 그 카메라로 계속 판단한다
- 재접속되면 그 좌석들은 **비어 있음에서 다시 시작**한다 (서버 재시작과 같은 규칙)
- 인원 계산에서는 빼고, 숫자 옆에 "n석 확인 불가"를 표시한다

**알려진 한계: 움직이지 않는 물건 오판**

- 의자에 걸린 옷·슬리퍼 같은 물건을 YOLO가 사람으로 잡으면, 계속 잡히기 때문에 5초/1분 타이머로는 거를 수 없다 (오히려 점유로 유지됨)
- 실험 v3에서 VLM이 뒤집은 오판 30개 중 28개가 적외선(밤) 사진, 20개가 신뢰도 0.5 이상이었다 (신뢰도 기준만으로는 못 거름)
- 강의실은 지정 학생이 열쇠로 관리해서 퇴실 시각이 정해져 있지 않다. 그래서 **"밤에는 무시" 같은 시간대 규칙은 쓰지 않는다**
- 2번은 YOLO만으로 구현하고, 대책은 VLM 확인(6번, 아래 "검토 중")과 YOLO 추가 학습으로 한다. `Seat`에는 "점유로 바꿔도 되나"를 묻는 지점을 따로 분리해 두어 나중에 VLM을 붙일 수 있게 한다

### 3. 교탁·복도 인원 (301호 광각 cam5)

- 광각 이미지를 **3분할**해서 탐지 (먼 곳의 작은 사람 탐지율을 높이기 위함)
  - 조각끼리 조금씩 겹치게 자르고, 결과를 원본 좌표로 되돌린 뒤 **NMS로 중복 박스 제거**
- 광각 이미지 위에 **교탁·복도 다각형 ROI**를 지정하고, 중심점이 그 안에 있는 사람만 센다
- YOLO는 전체 이미지(사각형)에서 탐지하고, 다각형 판단은 탐지 후 `cv2.pointPolygonTest`로 한다 (마스킹 방식은 경계의 사람이 잘려서 쓰지 않음)
- 프레임마다 값이 흔들리므로 **최근 N개 결과의 중앙값**을 표시

### 4. 총 인원 계산

카메라마다 담당 구역을 나눠 **중복 세기를 피한다.**

```
301호 총 인원 = 점유 좌석 수 + 확인 중 좌석 수 + 교탁·복도 인원 수
304호 총 인원 = 점유 좌석 수 + 확인 중 좌석 수
```

- 확인 중 좌석은 사람이 아직 교실 안에 있을 수 있어 **인원에 포함**
- 알려진 오차: 좌석을 떠나 교탁·복도로 가면 최대 1분간 두 번 세어짐. 처음에는 그대로 두고, 실제 데이터에서 자주 보이면 보정 규칙 추가

### 5. 트래킹은 쓰지 않는다

판단 기준이 "사람"이 아니라 "구역(좌석·교탁·복도)"이라 사람별 ID가 필요 없다. 트래킹은 높은 FPS가 필요하고, 강의실은 가림이 많아 ID 전환 문제가 잦다. 실제 데이터에서 오판(예: 여러 사람이 연달아 같은 ROI를 지나가 점유로 판단)이 자주 보이면 그때 Ultralytics `model.track()`(ByteTrack)으로 추가한다.

### 6. VLM (Ollama, 2~4B급)

- **강의실 상태 판단만** 담당: 수업 중 / 빈 강의실 / 개인 자습
- 좌석 판정에는 관여하지 않는다
- 느리므로 YOLO와 별도로 **몇 분 간격**으로 실행
- 판단 결과는 메모리에 최신값을 두고, 판단할 때마다 SQLite `room_state_log`에도 한 줄 기록한다
- **검토 중 (6번 구현 시 결정)**: 적외선 모드 카메라의 좌석이 5초 조건을 넘겨 점유로 바뀌려 할 때만 VLM에게 한 번 확인한다. 정해지면 위의 "좌석 판정에는 관여하지 않는다"에 이 예외를 적는다
  - 조건은 강의실 조명 판정이 아니라 **카메라별 적외선(흑백) 모드**로 본다 (오판의 직접 원인이므로)
  - 0.5초 추론 루프가 기다리지 않도록 별도 스레드에서 묻는다
  - 확인할 점: 불을 끄고 공부하는 실제 사람을 YOLO가 찾는지, VLM이 "사람"이라고 답하는지 (기존 데이터에 이런 장면이 없음)

### 7. 관리자 화면

- **카메라 영상은 띄우지 않는다** (개인정보 부담)
- 좌석 점유: 강의실 **배치도 위에 좌석 상태를 색으로** 표시 (비어 있음 / 점유 / 확인 중)
- 인원: 숫자로 표시
- 갱신: 처음에는 웹이 몇 초마다 **API를 호출하는 폴링** 방식 (응답 형식은 JSON, 값은 메모리에서 바로 가져옴). 나중에 WebSocket 고려
- 통계(시간대별 평균 인원 등)는 SQLite에서 조회한다

### 8. 조명 판정

픽셀 밝기 방식으로 결정 (301호·304호 평균 정확도 99% 이상). 강의실 열림/닫힘 판단에 사용 예정.

## 전체 처리 흐름

```
RTSP 상시 연결 (카메라별 스레드, 최신 프레임 유지)
  ├─ YOLO 짧은 간격 반복
  │    ├─ 일반 cam → 중심점 ROI 판단 → Seat 상태 갱신(타이머) → 좌석 상태
  │    └─ 광각 cam5 → 3분할 탐지 → NMS → 교탁·복도 다각형 판단 → 중앙값 → 인원 수
  └─ VLM 몇 분 간격 → 강의실 상태
        ↓
  메모리 (Seat 객체, 현재 인원, 최신 강의실 상태)
        ├─ 실시간 API ──▶ 관리자 웹 (폴링으로 배치도·숫자 갱신)
        └─ 1분마다 요약 ──▶ SQLite (room_log, room_state_log)
                                  └─ 통계 API ──▶ 관리자 웹 (통계 화면)

JSON (v2/config/) ── 프로그램 시작 시 읽기 ──▶ 좌석 ROI·배치도·교탁 ROI
```

| 좌석 정의 (고정)     | 좌석 번호, 배치도상 위치(x, y, w, h), 카메라별 ROI 다각형 | JSON      | v1에서 옮겨옴                                    |
| 교탁·복도 ROI (고정) | 광각 이미지 기준 다각형                                   | JSON      | 새로 지정                                        |
| 좌석 상태 (실시간)   | 좌석 번호, 현재 상태, 마지막 감지 시각                    | 메모리    | API로 바로 응답, 파일에 쓰지 않음                |
| 요약 로그            | 1분 단위 점유 좌석·인원                                   | SQLite    | 매초 결과를 다 저장하지 않음, 삭제하지 않고 보관 |
| 강의실 상태 로그     | VLM 판단 결과(수업 중/빈 강의실/개인 자습)                | SQLite    | VLM 실행 주기마다 한 줄                          |
| 점유 전환 기록       | 좌석 상태가 바뀐 순간의 프레임 전체 + 모든 박스(좌표, 신뢰도, 엉덩이 키포인트 유무, 적외선 여부) | 미정 (커밋 안 함) | 오판 분석·YOLO 추가 학습용. 학생 사진 포함 |

SQLite 표 구조 (초안):

```sql
-- 1분 단위 요약 (v1의 occupancy/*.json snapshots를 대체)
CREATE TABLE IF NOT EXISTS room_log (
    ts          TEXT    NOT NULL,  -- '2026-11-02 14:31' (분 단위)
    room        TEXT    NOT NULL,  -- '301', '304'
    occupied    INTEGER NOT NULL,  -- 점유 좌석 수
    checking    INTEGER NOT NULL,  -- 확인 중 좌석 수
    front_count INTEGER,           -- 교탁·복도 인원 (304호는 NULL)
    total       INTEGER NOT NULL,  -- 총 인원
    PRIMARY KEY (room, ts)
);

-- VLM 강의실 상태
CREATE TABLE IF NOT EXISTS room_state_log (
    ts    TEXT NOT NULL,
    room  TEXT NOT NULL,
    state TEXT NOT NULL,           -- '수업 중' / '빈 강의실' / '개인 자습'
    PRIMARY KEY (room, ts)
);
```

- 수집한 강의실 사진은 외장 SSD에 저장 (NAS 사용 안 함)
- 좌석은 지정석이라 책·인형 등 개인 물건이 상시 놓여 있음 (물건만으로 점유 판단하지 않는다)

## v1에서 참고할 것

v1 경로는 `HyoChan1117/person-count` 기준.

| v1 위치                                                                  | 내용                                                        | v2에서                                                                    |
| ------------------------------------------------------------------------ | ----------------------------------------------------------- | ------------------------------------------------------------------------- |
| `backend/data/classrooms.json` → `seat_lines`                            | 301호 좌석별 4점 다각형 ROI (CCTV 1~4, 30석)                | `v2/config/`의 좌석 ROI JSON으로 사용 (RTSP 주소·비밀번호는 옮기지 말 것) |
| `backend/data/map_data/1.json`                                           | 301호 배치도 (`type: "desk"`, `label`=좌석 번호, x/y/w/h)   | `v2/config/`의 배치도 JSON으로 사용                                       |
| `backend/app/services/frame_capture.py` → `_RTSPGrabber`                 | RTSP 수신·재연결 스레드                                     | 참고해서 재작성. **유휴 종료(`_IDLE_TIMEOUT`) 로직은 제거**               |
| `backend/app/services/vision_llm_detection.py` → `_is_in_seat_band()`    | 점이 다각형 안인지 판단                                     | 좌석·교탁 판단 공통 함수로 재작성                                         |
| `backend/app/services/vision_llm_detection.py` → `_run_seat_occupancy()` | ROI + 앉음 판단                                             | **앉음 조건(`sitting_flags`) 제거**하고 참고                              |
| `backend/app/services/live_stream.py` → `_LiveWorker`                    | 카메라별 상시 추론 워커                                     | 구조 참고. 출력을 JPEG → 탐지 결과로 변경                                 |
| `backend/app/storage.py` → `append_occupancy_snapshot()`                 | 10분 단위 점유 기록을 JSON 파일 전체에 다시 씀, 매주 초기화 | **참고하지 않음.** SQLite `room_log`로 대체                               |

주의: v1은 모든 카메라가 하나의 `infer_lock`을 기다리는 구조다. v2에서는 여러 카메라 프레임을 **묶어서(batch) 추론**하는 방식을 우선 고려한다.

v1에 없는 것: 304호 좌석 매핑, 광각 3분할 탐지 코드, SQLite 기록.

## 미정 (구현 후 결정)

- **YOLO 추론 간격**: 5초 진입 조건을 안정적으로 판단할 수 있는 간격을 만들어보고 결정 (0.5초 정도가 후보). `ENTER_GAP_SEC`(현재 1초)도 함께 조정
- **YOLO 모델 크기·imgsz**: 실험은 `yolo26x-pose.pt` + imgsz 1280 (가장 무거운 조합). 카메라 4대를 짧은 간격으로 추론해야 하므로 x/l/m, 640/1280 조합의 속도·정확도를 비교해서 결정
- **pose vs detect 모델**: 키포인트가 재확인 조건으로 쓸모없다고 확인되면 detect 모델로 바꾼다 (추가 학습 라벨이 박스만 있으면 되어 훨씬 쉬움)
- **적외선 VLM 확인**: 위 "6. VLM"의 검토 중 항목. 불 끄고 공부하는 장면을 팀원이 직접 재현해서 실험한 뒤 결정
- **추가 학습 흐름**: 신뢰도 낮은 박스·적외선 박스를 VLM이 판정 → 사람이 검토 → 추가 학습 → 학습에 안 쓴 날짜의 정답지로 YOLO만 평가. YOLO만으로 목표 정밀도가 나오면 VLM 좌석 확인을 끈다
- **점유 전환 기록의 저장 위치·보관 기간**: 학생이 찍힌 사진이 포함되므로 팀에서 결정 (외장 SSD 후보)
- **PTZ 역할**: 광각이 교탁 정반대(뒤쪽)에 있어 교탁 쪽 탐지가 약할 수 있음. 교탁 보조용 여부 판단
- **웹 프레임워크**: 미정
- **좌석별 기록(`seat_log`) 추가 여부**: "어느 좌석이 자주 비는지" 같은 좌석 단위 통계가 필요해지면 `seat_log(ts, room, seat, state)` 표를 추가 (1분 단위 30석이면 하루 약 4만 3천 줄)

## 구현 순서

1. RTSP 상시 연결 (카메라별 스레드, 최신 프레임 유지)
2. 좌석 점유: YOLO-pose → 중심점 ROI 판단 → Seat 상태 타이머
3. 교탁·복도 카운트 (301호): 3분할 탐지 → NMS → 다각형 판단
4. 총 인원 계산 + 1분 단위 요약을 SQLite `room_log`에 저장
5. 관리자 웹: 실시간 API(메모리) + 배치도 + 인원 숫자 (폴링)
6. VLM 강의실 상태 판단 (별도 주기) + SQLite `room_state_log` 저장
7. 통계 화면: SQLite 조회 (시간대·요일별 평균 인원 등)

2번 이후 추론 간격, 3번 이후 PTZ 역할을 결정한다.
